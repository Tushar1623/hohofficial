HOUSE OF HUMOUR (HoH) WEBSITE
CODEBASE SIMPLIFICATION + PRODUCT RESTRUCTURE PLAN

Repository:
Tushar1623/hohofficial

OBJECTIVE
=========
Simplify the existing HoH React/Vite website and restructure it around the actual requirement:

PUBLIC WEBSITE
1. HOME
2. PARTICIPATE
3. TICKETS

PRIVATE SYSTEM
4. ADMIN PANEL

The website should be simple, fast, reliable, mobile-first and easy to manage.

Do NOT rebuild the entire website from scratch.
Do NOT create a complicated entertainment portal.
Do NOT add unnecessary features.
Use the existing React/Vite foundation and remove unnecessary complexity.

==================================================
7. APP CONTEXT SIMPLIFICATION
==================================================

The current AppContext manages too much global state.

Reduce it dramatically.

Do not store the entire HoH database in global React Context.

Prefer:
Page → API service → Backend

Use global Context only for genuinely global state, such as:
- authentication/session
- small global UI state if required
- a global toast only if actually needed

==================================================
8. REMOVE ACTIVE EVENT COMPLEXITY
==================================================

Do not rely on a manually selected activeEvent if unnecessary.

Use events with:
published
dateTime

Then:
published events
→ future events
→ sort by dateTime
→ nearest future event
→ NEXT EVENT

If no future event exists:
Next HoH event coming soon.

The current demo event is dated 2 October 2026 and is already past as of 8 October 2026. Do not keep it as the permanent homepage default.

==================================================
9. EVENT DATA MODEL
==================================================

Use actual machine-readable data.

Example:

{
  title: "Mumbai Stand-Up Qualifier",
  city: "Mumbai",
  venue: "Example Venue",
  dateTime: "2026-10-18T19:00:00+05:30",
  prize: 20000,
  generalPrice: 499,
  vipPrice: 799,
  bookingUrl: "",
  published: true,
  status: "UPCOMING"
}

Do not store presentation-formatted dates as the primary data.
React should format date/time for display.

==================================================
10. API ARCHITECTURE
==================================================

Current prototype:
React → AppContext → api.js → storage.js → localStorage

Target:
React → api.js → Express/Node.js → MongoDB

Keep the service layer simple.

Example methods:
getNextEvent()
getEvents()
submitApplication()
getApplications()
updateApplication()
getFeaturedVideo()
updateFeaturedVideo()
getTicketSettings()
updateTicketSettings()
getSettings()
updateSettings()

Do not create multiple unnecessary service abstraction layers.

==================================================
11. DATABASE
==================================================

MongoDB should become the shared source of truth.

Participant submissions must not be stored only in browser localStorage.

Correct flow:

Participant Phone
→ React
→ POST /api/applications
→ Backend
→ MongoDB
→ Admin Laptop
→ GET /api/applications
